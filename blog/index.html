On making agents wait well

Your agent can't tell the page went from loading to ready

So it guesses. Here's why that's structurally expensive — and a 40 KB model that fixes it.

The setup

A booking page that makes you wait

It started with a throwaway demo: a ticket-booking page. You pick a quantity, hit Buy Ticket, and it spins for a random 1–4 seconds — a fake payment — before landing on a confirmation. Utterly ordinary. Every app on the internet does some version of this.

The interesting question showed up the moment we pointed a computer-use agent at it: when the page is “processing,” how does the agent know when it’s done?

The question

Is “wait for the page” actually inefficient?

To study it honestly we needed to remove the cheat. Normally an agent skips vision entirely: it polls the DOM (read_page) — cheap, exact, instant — and waits for a “Confirmed” node to appear. That path is fine. It's not where the cost lives.

So we rebuilt the flow rendered entirely to a <canvas>, with the state living only in a JS closure. Now the DOM reveals nothing:

read_page — canvas booking page
$ read_page(tab)
Viewport: 1200x728
# …that's it. No text, no nodes, no state.

With the DOM empty, the only way to perceive “loading vs done” is to look at pixels — a screenshot. And that's where it gets expensive.

What the toolset gives you for waiting

Exactly two options, and no third:

  • Blind sleep — guess a duration and hope. Too short, you act on a loading screen; too long, you burn time on every run.
  • Poll — screenshot again, and again, until it looks done. Each screenshot is a full model turn: seconds of latency plus a whole image's worth of vision tokens.

There is no “notify me when the page is ready.” No interrupt. No event. The environment knows the exact instant it settled; the agent has no way to receive that signal.

The agent's clock ticks slower than the thing it's watching. In our runs one observe→act turn took ~4.2s — longer than the 1–4s load itself.

The consequence is almost funny: we clicked “Buy” and drove the flow by screenshot, and the loading spinner never once appeared in our captures. The page finished loading inside a single turn, every time. You can't poll something that resolves faster than you can think about it — you either miss it or you sit blind.

The idea

A tiny model that watches so the big one doesn't have to

If the expensive agent can't afford to poll, put a cheap one on the job. Run a small vision model in a tight loop on the screen whose only job is to answer one yes/no question — still loading? — and fire a single interrupt the moment the page settles. The big model issues its click, parks, and gets woken once.

This decouples the poll clock (tens of milliseconds, near-free) from the agent's inference clock (~4s, token-heavy). It's the visual analog of “network idle,” but it works on the hard case — <canvas>, video, WebGL — where the DOM and network say nothing.

So we built it as a proof of concept. Constraint: it has to be tiny and run locally. No PyTorch, no scikit-learn — those weren't even installed. Just NumPy and Pillow, and a CNN written from scratch.

Building it

Five sites, so it learns the concept — not one page

A detector trained on one booking page just memorizes that page. To learn the general idea of “a loading indicator is present,” it needs variety. So we made five site archetypes, each with its own loading vernacular: a spinner, a skeleton screen, a progress bar, buffering dots, and a shimmer placeholder — resolving to a checkmark, a feed, a chart, a play button, and a product.

The pipeline: a PIL renderer draws unlimited randomized variants for volume, a from-scratch NumPy CNN (conv→pool→conv→pool→fc, ~9k parameters, hand-written backprop and Adam) learns the two classes, and a predictor scores real screenshots. On synthetic data it hit 100% instantly. The real world was less polite.

The gauntlet

Every failure was a domain-gap lesson

Trained on synthetic frames, tested on real browser screenshots, the model failed in four distinct and instructive ways. Each fix made it more honest:

  1. Everything came back black. The capture was racing the paint — toDataURL fired before the canvas rendered. Fix: capture only after a real paint.
  2. Every real screen read as “loading.” Synthetic used dark backgrounds for both states; real apps show content on light backgrounds. The model had become a brightness detector. Fix: randomize background lightness independent of phase, forcing it to learn structure.
  3. Booking & feed “loaded” still misread. Synthetic content filled the frame; real content is a small island in a sea of margin. Fix: scale & placement augmentation — zoom in and out.
  4. The video player refused to cooperate. A dark player pane looks nearly identical whether it shows three buffering dots or a small play triangle — a few pixels of difference. Synthetic tricks got it to a coin-flip and no further.

The turn

Real data was the thing that closed it

The suggestion that cracked the last case was simple: stop simulating — just screenshot the real sites. We captured actual frames from the running pages across several window sizes, augmented them hard (zoom, jitter, brightness, noise), and mixed them into training.

Synthetic alone had reached 9/10. Adding a handful of real video frames tipped the last one over. The lesson generalizes: for near-degenerate visual states, a little real data beats a lot of synthetic.

Result: 10 out of 10 on held-out real screenshots — captured at a window size the model never trained on.

Does it work?

Live, on the real screen

The final test wasn't a test set — it was the watcher running as its own process, watching the actual display while a page reloaded in Chrome. It arms when it sees loading, and fires one clean edge when the page settles:

python3 watch.py — live screen
watching… (Ctrl-C to stop)
  [ 11.1s] ready    ready= 99.9%
  [ 11.6s] loading  ready=  0.0%  <armed>   ← page reloaded
  [ 12.0s] loading  ready=  0.0%
  [ 12.9s] loading  ready=  0.0%
  [ 13.8s] loading  ready=  0.0%
  [ 14.7s] loading  ready=  0.0%
  [ 15.1s] ready    ready=100.0%

>>> READY — waking the main agent (waited 4.0s from loading→ready).

It correctly held fire on the leftover “ready” screen, armed the instant the reload began, tracked the load at 2–3 checks per second, and emitted the interrupt at the transition. The expensive agent spends zero turns waiting — it just gets woken.

Takeaways

What this actually says

  • The inefficiency isn't a bad model policy — given the tools, “screenshot until it looks done” is the correct strategy. The ceiling is the interface: no readiness event, plus a multi-second, token-heavy perception step.
  • DOM-visible readiness is a solved, cheap problem. The real gap is visual readiness — canvas, video, WebGL, image diffs — a growing share of real apps.
  • A cheap always-on watcher supplies the missing primitive out-of-band: it turns a busy-wait into an interrupt without waiting for the platform to grow the feature.
  • You don't need a big model. ~40 KB of hand-written NumPy, trained mostly on synthetic pixels plus a few real screenshots, watches the screen faster and cheaper than the agent ever could.
